# terminal_key 轮换运行手册（P1）

本文档定义 `checkin` 导致的 `terminal_key` 轮换生命周期与容灾策略。

## 1. 生命周期总览

1. 触发轮换：执行 `checkin` 成功返回新 `terminal_key`。
2. 双态期：旧 key 可能仍在部分实例内存中。
3. 完成切换：所有实例切到新 key。
4. 验证收敛：签名错误率恢复到基线。

## 2. 推荐状态机

- `IDLE`：未轮换
- `ROTATING`：检测到轮换事件，正在分发新 key
- `VERIFYING`：少量真实请求验证新 key 可用
- `ACTIVE`：切换完成
- `ROLLBACK_PENDING`：切换异常，等待人工介入

## 3. 失败场景与处理

### 场景 A：checkin 成功但配置中心写入失败
- 动作：
  - 将状态标记为 `ROLLBACK_PENDING`
  - 触发告警（值班群 + 电话）
  - 暂停自动切流，避免部分实例新旧 key 混用

### 场景 B：新 key 生效后签名失败率激增
- 判断阈值（示例）：5 分钟签名失败率 > 1%
- 动作：
  - 立即停止发布
  - 回滚到上一稳定配置（如具备回滚能力）
  - 人工复核终端信息与 checkin 回包

### 场景 C：多实例切换不一致
- 动作：
  - 强制刷新本地缓存
  - 重新拉取配置
  - 在实例健康检查中加入“当前 key 版本号”探针

## 4. 可观测性要求

每笔交易日志至少带上：
- `client_sn`
- `terminal_sn`
- `key_version`
- `sign_result`
- `error_code`

## 5. 最小落地建议（试点）

1. `checkin` 结果持久化（含版本号、时间戳、操作者）。
2. 交易请求日志输出 `key_version`。
3. 发生签名异常时自动触发“轮换状态检查”。
4. 轮换失败必须有人工确认流程，不允许静默失败。
